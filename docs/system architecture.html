Scout Platform

System architecture

Three-tier architecture. Eligibility is always determined server-side — the client never supplies profile data used for matching.

Client

React frontend

Vite · React · Tailwind CSS
  • Renders login, profile, and opportunities views
  • Toggles between eligible and all opportunities
  • Stores auth token only — no profile fields
HTTPS / REST
API gateway

Django REST API

Django · DRF · psycopg2
  • Validates auth token on every request
  • Looks up student profile server-side
  • ORM for CRUD, parameterized raw SQL for matching + tracking
TCP 5432
Database

Supabase (PostgreSQL)

Hosted Postgres · SQL editor
  • Database as source of truth for schema
  • Enforces uniqueness — no duplicate applications
  • Sensitive fields structurally separated (POPIA)

Eligibility request lifecycle

1

Client requestsGET /opportunities with bearer token — no profile data attached

2

Token validatedDjango decodes the token and identifies the student

3

Profile fetchedDjango reads current field of study, year, average from Supabase

4

Query executedRaw SQL match for eligible view, ORM filter for all view

5

Response returnedMatched or full opportunity list sent back as JSON

✓

Security correction applied

An earlier draft stored field_of_study, year, and average in browser LocalStorage and sent them as request parameters; a student could tamper with these values in devtools to see opportunities they don't qualify for. The corrected flow above stores token only client-side; Django re-reads profile data from the database on every request.
