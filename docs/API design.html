API design

REST endpoint reference and the request lifecycle for eligibility checks — the one path where the client's toggle choice determines the query strategy on the backend.

Auth & profile

students app FR1, FR8
POST/api/auth/register/PublicCreate account, trigger verification email
POST/api/auth/verify-email/PublicConfirm email, unlock full access
POST/api/auth/login/PublicVerify credentials, issue auth token
POST/api/auth/logout/StudentInvalidate session on this device
GET/api/profile/StudentRead profile, excluding sensitive fields
PATCH/api/profile/StudentUpdate field of study, year, average, etc.
GET/api/documents/StudentList uploaded documents
POST/api/documents/StudentUpload or replace a document

Request lifecycle — GET /opportunities

1
Client sends request

GET /opportunities?view=eligible with the bearer token in the header — no profile fields attached.

2
Token validated

Django's auth layer decodes the token and identifies the requesting student.

3
Profile fetched server-side

Django reads current field of study, year level, and average directly from Supabase — never from the request.

4
Query strategy branches on view

The two paths below are mutually exclusive per request.

view=eligible Raw SQL matching

Parameterized query against field of study, year level, and opportunity type.

view=all ORM query

Filtered to verified, active, and not-yet-closed listings only.

5
Response returned

Matched or full opportunity list serialized and sent back as JSON.
