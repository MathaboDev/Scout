0 · Corrections to the earlier draft

The earlier draft marked several built features as removed or planned. Check your diagrams against this list before you start.

  • Built, so keep: missing-document alert (in-app and email, once only, with a resume link), submission receipt email, outcome and status-change notifications, bookmarks (save, list, remove), application summary PDF, and the deadline reminder command.
  • Partly built: deadline reminders are a management command (send_bookmark_reminders). They run only when a scheduled job calls them. Draw it as a system job, not as a live feature.
  • Outcome wording: the outcome is Successful or Unsuccessful. Do not use Accepted or Rejected.
  • Eligibility type: eligibilitytype is never NULL. The value Any means open to both student types.
  • Adminid: opportunity.adminid is NOT NULL. On creation it is set to the first active admin. Verification overwrites it with the reviewing admin. It is not "null until verified".
  • Login_otp columns: the real names are user_id, code_hash, resend_token_hash, resend_count, created_at, expires_at, attempts, is_used. Not authuserid or codehash.
  • Not built, so remove: password reset, user management, listing or account suspension, platform monitoring.
Also correct the earlier brief The Diagram Revision Brief and Revised Diagram Reference (Markdown) say missing-document alerts, the summary download and auto-apply are planned. That is wrong for the first two. Update those files to match this page.

2 · Activity diagram: student application flow

Four swimlanes. Amber boxes are decisions. Grey dashed boxes are planned. The flow starts at signup and ends at the receipt and the status updates.

Remove
  • Resume application as a separate step. The alert links to /apply/<id>?resume=documents, so the student goes back into the same review flow.
  • Set reminder on bookmark as a student action. Reminders are a scheduled system job.
  • Sort by closing date as a separate step. It is part of the list query.
Fix
  • Verify email is a 6-digit code. A wrong code offers resend (max 3, 60 s cooldown, 5 attempts). A correct code signs the student in.
  • After verification the student goes straight to the dashboard. Do not route back through Login.
  • Generate receipt → Create application: status Submitted, reference number, receipt email.
  • Filter eligible names the real rule: verified, active, unexpired, matches field, type, average, year, qualification (or higher) and province.
Add
  • Returning login: an unverified account is told to verify first.
  • Already applied? check (409). One application per student per listing.
  • Missing documents branch: review shows the gap, sends the alert once, and blocks confirm (400).
  • Bookmark and Download summary PDF branches.
  • Provider and admin lanes (see sections 3 and 4).

3 · Sequence diagrams

Read each table top to bottom. Columns name the actor or system. Each row is one message, with the real endpoint.

Remove
  • "Receive verification link": it is a 6-digit code.
  • "Final decision: Accepted or Rejected" and "periodic updates": the outcome is Successful or Unsuccessful.
  • "Forward completed application to provider": providers pull applicants from the API.
  • "Admin platform monitoring": not built.
Fix
  • Listing verification: the provider creates via the API (pending). The admin pulls the queue and verifies it. The admin is the only writer of verification.
  • Lifelines: Student, Frontend, Django API, Database, Brevo SMTP, plus Provider and Admin.
Add
  • OTP signup with the valid and wrong/expired branches, plus resend.
  • Login with the unverified branch (403).
  • Duplicate application branch (409) and missing-document branch (400 on confirm).
  • Provider outcome notifies the student in-app and by email.

3a · Sign up and verify email (student or provider)

#FromToMessage
1Student / providerFrontendSubmit registration form
2FrontendAPIPOST /api/accounts/register/
3APIDatabaseInsert inactive auth_user, student or provider row, login_otp (hashed code, expires in 5 min)
4APIBrevo SMTPSend 6-digit code
5APIFrontend201, returns otp_id and resend_token
6FrontendStudentShow code entry screen
7Optional, resend: POST /api/accounts/resend-otp/. Max 3 resends, 60 s cooldown. Old code is replaced.
8StudentFrontendEnter 6-digit code
9FrontendAPIPOST /api/accounts/verify-otp/
10Alt, code valid: set is_active = true, mark code used, set student isemailverified, return token and user with role. Frontend stores it and opens the dashboard.
Alt, wrong, expired or used: 400 with error. Attempts count up. After 5 attempts the code is locked.

3b · Log in (no code) and open eligible opportunities

#FromToMessage
1StudentFrontendEnter email and password
2FrontendAPIPOST /api/accounts/login/
3Alt, valid and verified: token and user with role returned. Alt, valid but unverified: 403 "Please verify your email first". Alt, invalid: 401.
4FrontendAPIGET /api/opportunities/?view=eligible with token (or view=all)
5APIDatabaseLoad profile from the token (never the browser). Run matching query: verified, active, unexpired, rules in matching.py.
6APIFrontend200 with listings, each flagged eligible, bookmarked and applied

3c · Provider posts a listing, admin verifies it

#FromToMessage
1ProviderFrontendFill in listing form
2FrontendAPIPOST /api/opportunities/provider/listings/ (IsProvider)
3APIDatabaseInsert opportunity, isverified = false, adminid = first active admin (placeholder until verified)
4APIFrontend201. Listing shows as Pending verification.
5AdminFrontendOpen /admin/verify
6FrontendAPIGET /api/providers-admin/listings/pending/ (IsAdmin)
7AdminFrontendOpen detail panel, click Verify
8FrontendAPIPOST /api/providers-admin/listings/<id>/verify/
9APIDatabaseSet isverified = true and adminid = reviewing admin (audit)

3d · Assisted apply, confirm, and provider outcome

#FromToMessage
1StudentFrontendClick Apply on a listing
2FrontendAPIPOST /api/applications/review/ with opportunity_id
3Alt, required documents missing: can_submit = false, the missing list returned, and an alert sent once (in-app and email, with a link back to this review). Frontend shows the upload step.
Alt, all present: can_submit = true, pre-filled review returned.
4StudentFrontendCheck details, click Confirm
5FrontendAPIPOST /api/applications/confirm/
6Alt, already applied: 409 "already applied". Alt, closed: 410. Alt, missing documents: 400.
Alt, accepted: insert application (status Submitted, reference number). Receipt notification (in-app and email). 201 returned.
7ProviderFrontendOpen applicants for a listing
8FrontendAPIGET /api/applications/provider/listings/<id>/applicants/
9ProviderFrontendSet status (Under Review) or record outcome (Successful or Unsuccessful)
10FrontendAPIPATCH /api/applications/provider/applicants/<id>/. Forward moves only. Outcome final.
11APIBrevo SMTPStatus or outcome email to student. In-app notification also created.
12StudentFrontendOpen My applications. Dashboard polls /api/applications/mine/ and /api/notifications/.
Sources: applications/views.py, applications/urls.py, notifications/utils.py, accounts/views.py, providers_admin/views.py.

4 · Class diagram

Each class is a Django model mapped to one table, except the permission classes and the Django auth user. Methods are shown only where a view does more than a plain read or write.

Remove
  • Generic User with its own password. Login uses Django's auth_user.
  • AdminID on Opportunity Provider, which was the wrong key.
  • SummaryReport(), Close(), DeleteOpportunities(). These are view actions or fields, not model methods.
Fix
  • Opportunity Provider → Provider. Admin → PlatformAdmin (linked by email plus is_staff).
  • Opportunity fields: fieldofstudy, closingdate, eligibilitytype, and the optional criteria.
  • Notification belongs to Student, and optionally to an Application or a Bookmark.
  • Application links to Student and Opportunity. Both sides need a multiplicity.
Add
  • LoginOtp, Profile, Document, Bookmark, Notification
  • Permission classes IsStudent, IsProvider, IsAdmin (they attach the role row to the request)
  • Matched-by-email link between PlatformAdmin and auth user

5 · Entity relationship diagram

Database tables with lowercase column names, as in database/schema.sql. FK marks a foreign key. Shaded cards are Django's own table or a missing schema item.

Remove
  • ReceivedAt on Application (the columns are reviewedat and outcomereceivedat)
  • MininumAverage misspelling (minimumaverage)
  • Student passwordhash is legacy. Mark it unused.
Fix
  • opportunity.adminid is NOT NULL. Set to a placeholder on creation, overwritten when verified.
  • Eligibility type is never NULL. Any means both.
  • Notification FKs to application and bookmark are nullable, and at most one is set.
  • login_otp columns: user_id, code_hash, resend_token_hash, resend_count, created_at, expires_at, attempts, is_used.

  • Profile: studenttype, graduatetype, qualification
  • Opportunity: requiredqualification
